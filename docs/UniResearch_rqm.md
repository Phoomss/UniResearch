# UniResearch — Functional Requirements, Non-Functional Requirements และ RBAC Matrix

---

## 1. Functional Requirements (ความต้องการเชิงฟังก์ชัน)

### FR-1: การจัดการบัญชีผู้ใช้งาน (User Account Management)
- FR-1.1 ผู้ใช้งานสามารถสมัครสมาชิกและเข้าสู่ระบบได้
- FR-1.2 ผู้ใช้งานสามารถจัดการโปรไฟล์ของตนเองได้
- FR-1.3 ระบบสามารถแบ่งบทบาทผู้ใช้งานเป็น 4 ระดับ: ผู้เข้าชมทั่วไป, นักศึกษา/นักวิจัย, อาจารย์/ผู้ตรวจสอบ, ผู้ดูแลระบบ
- FR-1.4 ระบบต้องจำกัดสิทธิ์การใช้งานตามบทบาทของผู้ใช้ (Role-based Access Control)

### FR-2: การจัดเก็บผลงานวิจัย (Research Submission)
- FR-2.1 ผู้ใช้งาน (นักศึกษา/อาจารย์) สามารถเพิ่มข้อมูลผลงานวิจัยเข้าสู่ระบบได้ ประกอบด้วย: ชื่อเรื่อง (ไทย/อังกฤษ), บทคัดย่อ, ผู้จัดทำ, รหัสนักศึกษา, อาจารย์ที่ปรึกษา, สาขาวิชา, ประเภทผลงาน, ปีการศึกษา, คำสำคัญ, รูปภาพปก, ไฟล์ PDF
- FR-2.2 ผลงานหนึ่งชิ้นสามารถมีผู้จัดทำได้มากกว่า 1 คน
- FR-2.3 ระบบสามารถแก้ไขข้อมูลผลงานที่เคยเพิ่มไว้ได้
- FR-2.4 ระบบสามารถจัดเก็บไฟล์ฉบับแก้ไข (revision) เพิ่มเติมในอนาคตได้
- FR-2.5 ระบบสามารถอัปโหลดไฟล์ PDF ของผลงานได้

### FR-3: การค้นหาและกรองผลงาน (Search & Filter)
- FR-3.1 ผู้ใช้งานสามารถค้นหาผลงานจาก: ชื่อเรื่อง, ผู้จัดทำ, อาจารย์ที่ปรึกษา, คำสำคัญ, หมวดหมู่, สาขาวิชา, ปีการศึกษา, ประเภทผลงาน
- FR-3.2 ระบบสามารถเพิ่มตัวกรอง (filter) เพื่อจำกัดผลการค้นหาให้ตรงประเด็นมากขึ้น

### FR-4: การแสดงรายละเอียดผลงาน (Research Detail View)
- FR-4.1 ระบบแสดงข้อมูล: ชื่อผลงาน, ผู้จัดทำ, อาจารย์ที่ปรึกษา, บทคัดย่อ, คำสำคัญ, ปีการศึกษา, ประเภทผลงาน, หมวดหมู่, จำนวนเข้าชม, จำนวนดาวน์โหลด, ไฟล์เอกสาร, ผลงานที่เกี่ยวข้อง
- FR-4.2 ระบบต้องแสดงผลงานที่เกี่ยวข้อง (related works) โดยอัตโนมัติ

### FR-5: การอัปโหลด/ดาวน์โหลดเอกสาร
- FR-5.1 นักศึกษา/อาจารย์สามารถอัปโหลดไฟล์ผลงานได้
- FR-5.2 ผู้เข้าชมสามารถเปิดอ่าน/ดาวน์โหลดเอกสารที่ได้รับอนุญาตให้เผยแพร่ได้
- FR-5.3 ระบบต้องบันทึกจำนวนการดาวน์โหลดของแต่ละผลงาน

### FR-6: การตรวจสอบและอนุมัติผลงาน (Review & Approval Workflow)
- FR-6.1 ผู้ตรวจสอบ/ผู้ดูแลระบบสามารถตรวจสอบความครบถ้วนและถูกต้องของข้อมูลก่อนเผยแพร่
- FR-6.2 ระบบต้องรองรับสถานะผลงาน: ฉบับร่าง, รอตรวจสอบ, ต้องแก้ไข, อนุมัติแล้ว, ไม่อนุมัติ, เผยแพร่แล้ว
- FR-6.3 ผู้ตรวจสอบสามารถส่งความคิดเห็น (comment) กลับไปยังผู้จัดทำเพื่อให้แก้ไข

### FR-7: การจัดหมวดหมู่ (Category Management)
- FR-7.1 ผู้ดูแลระบบสามารถเพิ่ม/แก้ไข/ลบหมวดหมู่ผลงาน (เช่น AI, Web Application, Mobile Application, Data Science, IoT, Software Testing, Cybersecurity, UX/UI Design)
- FR-7.2 ผู้ใช้งานสามารถสำรวจผลงานตามหมวดหมู่ได้

### FR-8: การบันทึกผลงานที่สนใจ (Favorites/Bookmark)
- FR-8.1 ผู้ใช้งานที่เข้าสู่ระบบสามารถบันทึกผลงานลงในรายการโปรดได้
- FR-8.2 ผู้ใช้งานสามารถเรียกดูรายการโปรดของตนเองภายหลังได้

### FR-9: หน้าแรก / ผลงานแนะนำ (Homepage & Recommendation)
- FR-9.1 ระบบแสดงผลงานล่าสุด
- FR-9.2 ระบบแสดงผลงานยอดนิยม / เข้าชมมากที่สุด / ดาวน์โหลดมากที่สุด
- FR-9.3 ระบบแสดงผลงานแนะนำประจำสัปดาห์ และหมวดหมู่ที่กำลังได้รับความสนใจ

### FR-10: สถิติและ Dashboard สำหรับผู้ดูแล
- FR-10.1 ผู้ดูแลระบบสามารถดูสถิติ: จำนวนผลงานทั้งหมด, จำนวนผู้จัดทำ, จำนวนอาจารย์ที่ปรึกษา, จำนวนเข้าชม, จำนวนดาวน์โหลด, จำนวนผลงานต่อปี/ต่อหมวดหมู่, คำค้นหายอดนิยม
- FR-10.2 ระบบต้องมีหน้า Dashboard สำหรับสรุปข้อมูลภาพรวม

### FR-11: การจัดการผู้ใช้งานโดยผู้ดูแลระบบ
- FR-11.1 ผู้ดูแลระบบสามารถจัดการผู้ใช้งาน, หมวดหมู่, ผลงาน, เอกสาร และข้อมูลทั้งหมดในระบบ

## 2. Non-Functional Requirements (ความต้องการที่ไม่ใช่เชิงฟังก์ชัน)

| รหัส | หมวด | รายละเอียด |
|---|---|---|
| NFR-1 | Usability | ระบบต้องใช้งานง่าย มีหน้าตาทันสมัย (Modern UI/UX) เหมาะกับผู้ใช้หลากหลายกลุ่ม (นักศึกษา อาจารย์ นักวิจัย บุคคลทั่วไป) |
| NFR-2 | Localization | ระบบต้องรองรับ 2 ภาษา คือ ภาษาไทยและภาษาอังกฤษ ทั้งเนื้อหาข้อมูลและส่วนติดต่อผู้ใช้งาน |
| NFR-3 | Accessibility | ระบบต้องเข้าถึงได้ผ่านเว็บเบราว์เซอร์ (Web-based) โดยไม่จำกัดเฉพาะบุคลากรภายในมหาวิทยาลัย (รองรับบุคคลทั่วไป) |
| NFR-4 | Security & Access Control | ระบบต้องจำกัดสิทธิ์การเข้าถึง แก้ไข และอนุมัติข้อมูลตามบทบาทผู้ใช้งานอย่างรัดกุม เพื่อป้องกันการแก้ไขหรือเผยแพร่โดยไม่ได้รับอนุญาต |
| NFR-5 | Data Integrity | ข้อมูลผลงาน ผู้จัดทำ และอาจารย์ที่ปรึกษาต้องถูกต้อง ครบถ้วน และเป็นระบบ ป้องกันข้อมูลสูญหายเมื่อผู้จัดทำสำเร็จการศึกษา |
| NFR-6 | Performance | ระบบต้องรองรับการค้นหาและกรองข้อมูลจำนวนมากได้อย่างรวดเร็วและตรงประเด็น |
| NFR-7 | Storage / Centralization | ระบบต้องทำหน้าที่เป็นคลังข้อมูลกลาง (Central Repository) แทนการจัดเก็บกระจัดกระจายในคอมพิวเตอร์ส่วนตัวหรือ Google Drive |
| NFR-8 | Reliability | ระบบต้องบันทึกสถิติการเข้าชม/ดาวน์โหลดได้อย่างแม่นยำ เพื่อใช้วิเคราะห์แนวโน้มได้อย่างน่าเชื่อถือ |
| NFR-9 | Scalability / Maintainability | ระบบต้องออกแบบให้สามารถต่อยอดฟังก์ชันขั้นสูงในอนาคตได้ เช่น AI สรุปงานวิจัย, ตรวจสอบการคัดลอก (plagiarism check), ระบบแนะนำผลงาน, การสร้างรูปแบบอ้างอิงอัตโนมัติ |
| NFR-10 | File Support | ระบบต้องรองรับไฟล์รูปแบบ PDF สำหรับเอกสารงานวิจัย และไฟล์รูปภาพสำหรับปกผลงาน |

## 3. RBAC Matrix (Role-Based Access Control)

สัญลักษณ์: ✔ = ทำได้ | ✘ = ทำไม่ได้ | ✔* = ทำได้เฉพาะข้อมูล/ผลงานของตนเอง

### Authentication
| ฟังก์ชัน / สิทธิ์ | Guest | Student | Advisor | Admin | หมายเหตุ |
|---|---|---|---|---|---|
| สมัครสมาชิก / เข้าสู่ระบบ | ✔ | ✔ | ✔ | ✔ | guest ใช้ได้เพื่อสมัครเป็น student |
| ออกจากระบบ / รีเฟรช token | ✘ | ✔ | ✔ | ✔ | |

### User Profile / User Management
| ฟังก์ชัน / สิทธิ์ | Guest | Student | Advisor | Admin | หมายเหตุ |
|---|---|---|---|---|---|
| ดู/แก้ไขโปรไฟล์ของตนเอง | ✘ | ✔ | ✔ | ✔ | |
| ดูรายชื่อผู้ใช้งานทั้งหมด | ✘ | ✘ | ✘ | ✔ | |
| เพิ่ม/แก้ไข/ลบผู้ใช้งาน และเปลี่ยน role | ✘ | ✘ | ✘ | ✔ | |

### Research Submission

|---|---|---|---|---|---|
| สร้างผลงานวิจัยใหม่ (สถานะ draft) | ✘ | ✔ | ✔ | ✔ | |
| แก้ไขผลงานของตนเอง (draft/needs_revision) | ✘ | ✔* | ✔* | ✔ | admin แก้ไขได้ทุกผลงาน |
| แก้ไขผลงานของผู้อื่น | ✘ | ✘ | ✘ | ✔ | |

| อัปโหลดไฟล์ฉบับแก้ไข (revision) | ✘ | ✔* | ✔* | ✔ | |
